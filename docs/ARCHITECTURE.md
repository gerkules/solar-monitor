# Архитектура

## Компоненты

```
                          ┌──────────────────────────────┐
 инвертор (Voltronic PI30)│           collector          │
   ├ USB-HID ────────────►│ transports: hid/serial/tcp/  │
   ├ USB-RS232 ───────────►│            mqtt              │
   └ донгл EW10 (TCP) ────►│ poller (QPIGS/QPIRI/QBMS/…)  │
                          │ rules · notifier · forecast   │
                          └───────┬──────────────┬───────┘
                                  │ MQTT         │ HTTP (API + UI)
                                  ▼              ▼
                          ┌──────────────┐  ┌───────────────┐
                          │  Mosquitto   │  │ браузер / API │
                          └──────┬───────┘  └───────────────┘
                                 │ Home Assistant (discovery)
                                 │ line protocol
                                 ▼
                          ┌──────────────┐        ┌────────────┐
                          │  InfluxDB    │───────►│  Grafana   │
                          └──────────────┘        └────────────┘
```

Один контейнер `collector` = один инвертор (сайт). Масштабирование на несколько инверторов —
это несколько контейнеров с одинаковыми InfluxDB/Grafana (см. [INTEGRATIONS.md](INTEGRATIONS.md)).

## Поток данных

1. **Опрос.** `poller` в цикле (`POLL_INTERVAL`, по умолчанию 5 с) отправляет кадры PI30 через
   транспорт: `QPIGS` (+`QPIGS2` для второго MPPT), реже `QMOD` (60 с), `QPIRI` (600 с),
   `QPIWS` (60 с), `QBMS` (60 с). Ответы проверяются по CRC и по «правдоподобности» кадра.
2. **Нормализация.** `pi30.py` парсит кадры в плоский словарь (`battery_voltage`, `pv_power_2`, …),
   `energy.py` досчитывает производные (мощность АКБ из U·I, мощность сети из баланса) и суточные
   счётчики кВт·ч.
3. **Публикация.** `publishers.py` отдаёт состояние в MQTT (общий JSON + по топику на метрику +
   discovery для HA) и пишет строку line protocol в InfluxDB.
4. **API/UI.** `webapp.py` (FastAPI) отдаёт JSON API, SSE-поток состояния, историю из InfluxDB и
   статический SPA-интерфейс. История читается запросами Flux (2.x) или InfluxQL (1.8).

## Ключевые решения

| Решение | Почему |
|---|---|
| Один процесс на инвертор | инвертор — один последовательный порт; два опросчика конфликтуют кадрами |
| PI30-парсеры со строгой валидацией | на общем UART (инвертор + ESP32 + SolarAssistant) в ответ может прийти чужой кадр с валидным CRC |
| Уставки с проверкой чтением (QPIRI) | инвертор отвечает `(ACK)`, но может не применить значение; «Saved» без read-back — ложь |
| Список кодов из мануала в приложении | владельцу не нужно искать мануал, а ошибки BMS (60/69/70/71) читаются прямо из `QBMS` |
| InfluxDB 1.8-совместимость | SolarAssistant использует 1.8, и на Synology 2.x зависает (bolt+btrfs) |
| `source: sa-mqtt` | можно забрать данные из уже работающей SolarAssistant, не отбирая у неё USB-порт |
| Мультисайт через MQTT + прокси | у каждого коллектора свой транспорт/уставки, а UI может ходить в API соседа по `?site=` |
| i18n на клиенте | язык интерфейса не должен зависеть от бэкенда |

## Файлы состояния (`/data` в контейнере)

| Файл | Что внутри |
|---|---|
| `energy.json` | суточные счётчики кВт·ч (сброс в полночь) |
| `rules.json` | правила автоматизации |
| `battery.json` | выбранный источник данных АКБ (из UI) |
| `bms_events.json` | журнал кодов BMS (последние 1000) |
| `connection.json` | выбранный транспорт/источник (из UI) |
| `forecast.json` | кэш последнего прогноза PV |

## Производительность (замеры на реальной системе)

* 4 ядра / 1.9 ГБ RAM достаточно для коллектора + InfluxDB + Grafana (VDS `192.168.31.115`).
* Контейнер коллектора: ~60–80 МБ RAM, CPU почти idle (опрос 5 с).
* История: ~30 метрик × 10 с ≈ 250 тыс. точек/сутки ≈ 1–2 МБ/сутки в InfluxDB.
* Страница «Графики»: 18 запросов истории на смену периода, кеш на период.
