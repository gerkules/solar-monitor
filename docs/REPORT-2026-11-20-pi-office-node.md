# Отчёт: узел на Raspberry Pi в офисе и интеграция с домашним контуром

Дата: 2026-11-20. Автор: агент (сессия в `~/solar-monitor`).
Область: офисный узел на Pi 1, публикация по MQTT, две новые страницы UI,
устойчивость и безопасность. Всё ниже — проверено на живом железе, не «по коду».

## 1. Топология (как есть на самом деле)

```
ДОМ                                                     ОФИС (4 км, Wi-Fi мост друга)
 сторонний «провайдер» 192.168.1.0/24  ← Starlink, L2 и DHCP у друга
   ├─ домашний роутер, WAN 192.168.1.222 (NAT; порт-форвард 9999)
   │    └─ своя сеть 192.168.31.0/24
   │         ├─ инвертор → донгл EW10 192.168.31.110:9999
   │         └─ NAS Synology  192.168.31.224  ← mosquitto, HA, данные
   │              └─ второй NIC: 192.168.1.224 (в том же «провайдерском» сегменте)
   └─ офис: Pi 1 `inverter11` 192.168.1.220 (DHCP), VDS `iptv` 192.168.1.145 (DHCP)
```

Ключевые следствия:

* `192.168.31.x` из офиса **не маршрутизируется** (NAT в одну сторону: из дома наружу можно,
  обратно — только через проброс порта на домашнем роутере).
* NAS живёт в обоих мирах (`31.224` и `1.224`) — это единственный узел, который видит всё.
* Сам «провайдерский» сегмент — чужая сеть: его нельзя считать доверенной LAN.

## 2. Что развёрнуто

| Узел | Роль | Как работает |
|---|---|---|
| Pi 1 (`inverter11`, `192.168.1.220`) | офисный инвертор, панель, **MQTT-хаб** | нативно под systemd: `solar-collector` + локальный `mosquitto`; инвертор по USB-HID `/dev/voltronic-inverter`; UI `:8080` |
| VDS (`iptv`, `192.168.1.145`) | домашний инвертор + UI обоих сайтов | Docker Compose: `solar-collector` (сайт `home`, TCP `192.168.1.222:9999` через проброс), Influx, Grafana, Caddy |
| NAS (`192.168.31.224` / `192.168.1.224`) | брокер дома, HA | mosquitto с паролем; получает `solar/home` и `solar/pi` **через мост с Pi** (исходящий с Pi, поэтому не нужен проброс) |

Поток данных: `инвертор офиса → Pi (USB) → брокер Pi`; `инвертор дома → донгл → проброс → VDS (TCP)
→ брокер Pi`; `Pi → мост → брокер NAS → HA дома`. В UI на VDS видны оба сайта.

## 3. Изменения в коде

### Мультисайт → «второй инвертор» из интерфейса
* `inverters.py` (новый): доп. инвертор = отдельный коллектор со своим `SITE`.
  Два режима: `systemd` (нативный хост, шаблон `solar-collector@.service` + helper
  `inverter-ctl` + sudoers) и `process` (Docker: дочерний процесс контейнера под
  супервизором). Конфиг `INVERTERS_DIR` (`/data/inverters`): `<site>.json` + `<site>.env`,
  свои файлы состояния, наследование общих настроек из основного `.env`.
* `sites.py`: настроенный, но ещё не публиковавший state инвертор виден в списке сайтов
  (кеш 10 с + сброс при create/update/remove) — площадка появляется сразу.
* UI: страница **Настройки → Инверторы** (список, старт/стоп/рестарт/удаление, форма
  добавления с проверкой связи и интервалом опроса).
* USB-HID: у Voltronic одинаковые VID:PID и `SerialNumber=0`, поэтому различает только
  порт. `deploy/pi/60-voltronic-hid.rules` даёт `/dev/voltronic-inverter` (первый) и
  `/dev/inverter-usbN` по порту; `inverter-ports` печатает порт ↔ hidraw ↔ алиасы ↔ кто
  занял; `free_hid_device()` не даст двум коллекторам открыть один узел (и его алиас).

### «MQTT» из интерфейса
* `mqttadmin.py` (новый) + `deploy/pi/mqtt-ctl` (root-helper, sudoers `solar-mqtt`):
  * «куда публикует этот коллектор» — host/port/логин/пароль/TLS/префикс, оверрайд
    `/data/mqtt.json` (перекрывает `.env`), сохранение = перезапуск процесса;
  * «брокер на этом хосте» — статус, порты, клиенты, анонимный доступ, пользователи
    (файл прав `zz-broker-ui.conf` читается последним, чтобы не конфликтовать с `listener`);
  * «мосты» — CRUD, направления `in/out/both`, фильтр топиков, откат при ошибке.
  * В Docker брокер/мосты только для чтения (это видно в UI), своё подключение работает.

### Исправления поведения
* `poller.py`: при исключении цикла транспорт закрывается — после USB re-enumeration
  hidraw переоткрывается сам (раньше процесс «залипал» на протухшем fd до рестарта).
* `poller.health()`: `ok` = «данные свежее `OFFLINE_AFTER`», а не `fails == 0` — единичный
  пропуск опроса больше не даёт HTTP 503 и не дёргает healthcheck/watchdog.
* `auth.py`: кеш успешных проверок (10 мин) и неудачных (1 мин) + предохранитель после
  5 неудач за минуту. Причина: PBKDF2-200k на Pi 1 = ~6 с CPU **на каждый** HTTP-запрос
  (Basic приходит с каждым файлом), ядро уходило в 100 %, страница рисовалась без CSS.
* `i18n.js`: в русский блок попали строки en/el (JS берёт последнее значение) — баннер
  «пароль по умолчанию» показывался по-гречески. Ключи разложены по языкам.
* `main.py`: `faulthandler` по `SIGUSR1` — дамп стеков всех потоков в журнал (так и найден
  виновник тормозов).

### Эксплуатация на Pi
* `deploy/pi/nftables.conf` + `console-font.service` + `solar-watchdog.sh` (таймер 2 мин):
  панель `8080` открыта в сегменте `192.168.1.0/24` (длинный пароль), брокер `1883` — только
  VDS/NAS; шрифт консоли `CyrAsia-Terminus16`; watchdog перезапускает коллектор только если
  API реально не ответил (раньше считал `503` за падение и перезапускал зря).

## 5. Безопасность

* Брокер на Pi: `allow_anonymous false`, пользователь `solar`; коллектор и VDS ходят с логином.
* Панель Pi: пароль не заводской (PBKDF2 в `/data/auth.json`), `ALLOW_SETTINGS=false`.
* Пароли **не** в git и не в этом отчёте: `/data/mqtt.json` (0600) и `/data/auth.json` на
  устройствах. В репозитории их нет (проверено `git grep` по истории).

## 7. Диагностика (шпаргалка)

```bash
# Pi
inverter-ports                      # порт ↔ hidraw ↔ алиасы ↔ кто занял
systemctl status solar-collector mosquitto nftables
curl -s localhost:8080/healthz      # ok/online/age_s/fails/mqtt_connected
kill -USR1 $(systemctl show -p MainPID --value solar-collector)   # стеки потоков в journal
journalctl -t solar-watchdog -n 20
sudo -n /usr/local/lib/solar-monitor/mqtt-ctl status
# данные
mosquitto_sub -h 127.0.0.1 -u solar -P '***' -t 'solar/#' -v
```

## 8. Осталось (не блокирует)

1. DHCP-резервации у владельца сети: `1.220` (Pi), `1.224` (NAS), `1.222` (домашний роутер) —
   иначе при смене аренды мост/доступ отвалится.
2. Проброс `1.222:9999` на домашнем роутере открыт всему «провайдерскому» сегменту — домашний
   инвертор читается через него. Убрать можно, опрашивая домашний инвертор из дома (NAS) либо
   подняв WireGuard/Tailscale между NAS и Pi.
3. `solar-collector-office` на VDS (`:8081`, sa-mqtt → `192.168.1.134`) — `unhealthy` и дублирует
   Pi; можно выключить.
4. Неверный пароль панели на Pi стоит ~6 с CPU; после 5 неудач за минуту вход замораживается на
   минуту (сделано намеренно).
5. EMI-сбросы USB (`disabled by hub (EMI?)`) на порту инвертора остаются — лечатся кабелем/портом,
   коллектор их переживает.
